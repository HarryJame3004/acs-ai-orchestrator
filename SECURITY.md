# Security Policy & Hardening Guidelines

## 1. Security Architecture & Threat Model

ACS AI operates as an autonomous agent orchestrator capable of modifying code, managing git branches, and invoking external CLI models. Because autonomous code execution poses inherent security risks, ACS AI is built around a **fail-closed, defense-in-depth security model**.

### 1.1 CoreLock Guard (Path Immutability)
- **Principle**: Critical base projects and system libraries are designated as immutable.
- **Enforcement**: The path `/home/khoi/autonomous-coding-system` is protected by `RepoManager` and `AutonomousMissionPlanner`. Any operation attempting to target this path as a writable workspace immediately aborts with a `PermissionError` and an audit alert.
- **Verified by Test**: `tests/test_gate8_natural_language_and_v2_2.py::test_repo_manager_rejects_protected_acs_core`

### 1.2 Fail-Closed Independent Guardian
- **Principle**: No code generated by an AI worker may merge to an integration branch without passing strict, independent criteria evaluated by the Guardian gatekeeper.
- **Rules**:
  1. Automated tests must execute and exit with code `0`.
  2. Modified files must not exceed the allowed scope defined in the task specification.
  3. No secrets, credentials, or dangerous command patterns may be introduced.
  4. Composite quality score must meet or exceed `0.85`.
  5. The HMAC-SHA256 evidence signature must verify against the local orchestrator secret.
- **Verified by Test**: `tests/test_gate5_guardian_and_security.py`

### 1.3 Cryptographic Evidence Binding (HMAC-SHA256)
- **Principle**: All evidence of task execution (diffs, test execution logs, exit codes, and commit SHAs) is bundled into a canonical JSON payload and cryptographically signed using HMAC-SHA256.
- **Protection**: Prevents tampering with test logs or falsifying successful execution outcomes.

### 1.4 Worker Sandboxing & Process Isolation
- **Bubblewrap Sandboxing**: Worker processes (e.g. `codex-primary`) execute inside restricted Linux bubblewrap (`bwrap`) containers:
  - Read-only mounts for system binaries (`/usr`, `/bin`, `/lib`).
  - Read-write access strictly confined to the task worktree.
  - Network access restricted where applicable.
  - Process isolation prevents worker child processes from accessing system daemon sockets.
- **Profile Isolation**: `agy-google-b` executes with an isolated `HOME` environment (`~/.local/share/acs-orchestrator/agy_b_home/`) to isolate credentials, cookies, and local caches.

### 1.5 Credential Masking & Secret Leak Prevention
- **Automatic Interception**: `MCPManager` audits all connected and usable MCP servers and tools.
- **Sanitization**: All GitHub PATs (`github_pat_*`), OpenAI keys (`sk-*`), Anthropic tokens, and Google API keys are stripped or masked prior to being written to logs, SQLite database, or TUI displays.

### 1.6 Human Approval Gate for Remote Operations
- **Principle**: Local autonomy is permitted within isolated git branches, but external side effects (such as `git push` to remote GitHub repositories or destructive system modifications) require explicit human approval.
- **Action**: The action transitions to `WAITING_APPROVAL` in SQLite and requires human sign-off via `acsai approval approve <id>`.

## 2. Security Best Practices for Operators

1. **Never Commit Real Credentials**:
   - Use environment variables or local secure keyrings.
   - Use `.env.example` as a template; never commit `.env` or files matching `*.token` or `*.secret`.
2. **Review Worker Prompts**:
   - Ensure natural-language mission prompts do not request destruction of uncommitted work.
3. **Keep Worktrees Clean**:
   - Worktrees are stored under `~/.local/share/acs-orchestrator/worktrees/`. Verify that unmerged worktrees are pruned when missions complete.
4. **Monitor SSD Storage**:
   - The SSD Circuit Breaker triggers if free storage falls below 10.0 GB, blocking new missions until disk space is reclaimed.
